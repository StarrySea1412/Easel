# 运营Agent可靠性追赶路线 · 2026-11-02

当前定位：有界面和执行机制，可监督试用；尚未证明能稳定承担无人值守运营。下一阶段优先完成「可信数据→分析→文案→图片→待确认草稿」，以真实任务结果衡量进展。更多界面、平台、执行器和角色能力在这条主链路达到门槛后推进。

## 2. 对标方式和架构取舍

沿用[四产品比较](agent-products-comparison-and-integration-2026-10-22.md)中已经核对的设计参考，不宣称做过同题实机竞赛或已达到原生产品可靠性：

- DeepSeek Harness：落实事件、工具调用、结果、执行归属和中断的契约，并通过故障注入检验。
- Codex：学习清晰的轮次和工具状态、审批及恢复边界；现有可选适配器继续隔离验收。
- Grok Bot：把长期角色和交接落实到有来源、有产物、有验收的运营任务。
- ZCode：让目标、预算、验收证据和可控经验贯通普通工作流。

追赶对象是可靠的工作方式。运营专长应体现在数据口径、账号隔离、品牌要求、素材来源和效果回填。现阶段扩展通用平台面会增加尚未验收的组合。

沿用现有运行账本、图片队列、分析库、交接与发布回执，不再另建并行任务系统。默认先认证一个「引擎+模型+渠道」组合，其他路径保留能力标识和独立验收状态；不静默更换用户所选渠道。模型负责理解诉求、规划和内容判断；身份、数据版本、费用预算、工具参数、重试规则、文件保存和完成判定由程序执行。

## 3. 按依赖排序实施

| 阶段 | 具体整改 | 进入下一阶段的证据 |
| --- | --- | --- |
| P0 资源与故障可见 | 追踪`llama-server`及记忆子进程的启动者、用途、峰值、退出及重启；分别观测Web/Gateway/浏览器/记忆/生成worker。按实测确定独立预算或隔离方式，在任务受理前做容量判断。可选记忆检索不可用时明确降级，涉及记忆写入时不可假装保存成功。 | 在隔离环境复现并验证内存压力与子进程退出；能定位所属组件并保持已受理任务可核对。无OOM、无静默丢任务、无资源永久泄漏。保留主机其他服务的资源预算，不能只不断提高容器上限。 |
| P1-A 数据取得和完整性 | 先认证一个主平台及一个明确数据窗口；在权限可用时接官方API，支持后台导出文件导入，受控浏览器采集独立标示来源。按稳定ID增量分页、保存游标/去重及失败断点；统一账号、指标定义、时间范围、抓取时间、缺失字段、样本范围和完整性契约。 | 对照平台后台/导出逐项核对。数量不足、取到一页、登录失效、验证码、限流和真实空结果可区分；旧数据不被失败覆盖，换账号不串数据。缺少效果数据时不生成效果归因。 |
| P1-B 生成及工具恢复 | 在支持查询的通道中，于提交回执到达后立即持久保存供应商任务ID、渠道身份及非秘密请求摘要。将提交、查询、下载、校验、交付分开；接回只查询原任务，下载失败仅重试下载。明确生图/排版能力和实际输出类型；等待输入、排队、执行、未知、完成分别展示。 | 提交前断线、已接受后进程退出、下载失败、数据库写入失败、刷新重连均有隔离证据；不多发一次收费请求。交付必须有可解码实际图片及保存回执。供应商不支持查询或提交结果不明时，保留待核验和明确处理入口。 |
| P2 运营单链路 | 固定输入数据版本；分析引用原字段，写作保留来源和品牌要求，图片绑定对应文案/素材版本，最后形成可人工确认草稿。已有交接机制扩展单步重试与检查点；返工只影响该步骤及依赖它的后续步骤。 | 数据/文案变更使依赖的旧验收失效；换页/刷新/进程重启不丢已完成产物。数据不足先补材料，生成失败定位到步骤，不重做采集或重放发布。 |
| P3 持续任务与扩容 | 冻结同一候选，完成代表性真实任务观察，再增加平台、渠道、并行及角色。平台实际发布和效果回填作为独立后续验收。 | 满足下方真实任务门槛；新增组合重新认证。草稿完成、已提交平台、已公开发布、效果已取得分别记录。 |

P0和P1应先产出可复核实现与故障证据；不因计划中有状态字段、接口或测试数量便宣布完成。真实平台权限、可查询的供应商协议和模型稳定性分别是外部条件，无法通过增加提示词保证。

## 4. 重试、降级和完成的统一规则

- 数据读取：仅对可重试的网络/限流等错误有界退避，按平台/账号共享限额；认证、账号不符、结构变化转人工处理。使用缓存须展示原抓取时间与范围。导入是明确选择的数据来源，不能静默拼成同一次完整采集。
- 模型生成：先区分请求未发送、明确拒绝、已接受及状态未知。只在证明未接受或供应商幂等契约允许时重试创建；能力不符/畸形工具调用不靠无限重跑解决。已完成副作用不重放。
- 图片：生成、下载和交付分开处理。换模型/渠道会改变质量、费用及身份，须依据明确的用户选择，不能作为隐藏重试。
- 完成判定：分析有输入与引用，文案有实际保存版本，图片有实际文件，草稿有对应素材。模型说“已完成”、HTTP200或进程退出0均不足以单独判定运营任务成功。
- 成本与时限：记录排队、供应商等待、工具执行和等待人工各自耗时；预算耗尽停止新派发，保留已产生结果及待核对状态。每个任务有明确的下一步，不能无限转圈。

## 5. 验收和度量

以下均为拟定门槛，不是本项目已经取得的成绩，也不是竞品实测数据。先测基线，再据实调整承诺。

1. 建立20个固定运营任务：5个数据取得/核验、5个有依据分析、5个文案与图片、5个交接/恢复。固定账号范围、数据版本、期望产物和人工评价规则；可离线部分用脱敏替身，真实平台与模型部分单独记录。
2. 每项运行覆盖相应故障矩阵：断网、限流、登录过期、部分分页、工具参数错误、供应商接受后失联、下载失败、worker死亡、Web重启、刷新、取消及重复观察。检查原请求次数、实际产物和资源结算，不能只检查最终文案。
3. 在同一冻结候选上完成受影响后端与完整回归门槛，再做真实浏览器的登录、菜单/跳转、待答、单步恢复与窄屏。现有审批/窄屏缺口须逐项补验。
4. 真实试用先做48小时有效负载观察，再累计7天、至少100个代表性任务；按平台、渠道、任务类型分别报告。目标为至少95/100在限定恢复和预算内完成，且重复收费/重复发布、跨账号串数据、已确认产物丢失、把错误结果报成功均为0；出现这类严重问题立即阻断扩容。该样本只支持观察结论，不能当作长期SLA保证。
5. 真实调用继续遵守已有费用与平台操作授权。当前没有代表性真实生图与平台闭环成绩，不能通过反复重放用户历史任务补数字。

统一统计口径：

| 指标 | 口径 |
| --- | --- |
| 首次完成率 | 第一次执行即通过文件/数据和人工质量验收的任务数 / 已受理有效任务数 |
| 有界恢复完成率 | 在限定时间、次数和费用内恢复并通过同一验收的任务数 / 同一任务集合；包含首次完成，不与其相加 |
| 人工介入 | 记录需重新登录/补材料/核对扣费/重新编排的次数及原因；预先声明的最终草稿确认单列 |
| 数据完整性 | 已取得作品/页数、已知总数、时间窗口、必需字段覆盖率；总数未知时保持未知，不给虚假的完整百分比 |
| 生成可靠性与质量 | 技术交付与人工可用分别记；空文件、类型错误、不可下载或缺来源不计技术成功，视觉/内容不合格另记 |
| 代价 | 每个任务的耗时、重试和实际可核对费用；未知费用保留未知，不能以估算替代供应商账单 |
| 资源稳定性 | 组件内存峰值、OOM/退出、队列等待、悬挂任务和租约结算；同时报告任务量，排除仅空闲在线的误读 |

取消、等待授权、缺外部权限/材料等逐项列出，避免从分母中静默剔除。恢复率提高但人工负担、耗时或费用失控，也不能算运营体验稳定。
