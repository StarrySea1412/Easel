# 0.45.8 隔离稳定性与并发读取评估

## 结论

账本快照和事件页的只读路径现在使用普通SQLite读事务，避免只读请求彼此争抢写意向锁。写锁持有期间读取回归通过。混合负载下读请求指标有温和改善趋势且所有请求成功，但单轮波动明显、最大读取延迟仍为2.1秒；写侧吞吐约3.4–5.4次/秒，未达到压测线程尝试的50次/秒节奏。**当前证据只支持本机隔离路径具备功能正确性，不能证明性能达标、长期可靠性或运营级/生产稳定。**

没有对138、真实模型、第三方平台或收费生成施压；没有部署138或发布安装包。

## 实现与回归

- 对已经初始化的账本，`read()` 和 `event_page()` 使用普通 `BEGIN` 只读事务，使读取可与其他读者共存，也允许在写事务持有SQLite reserved lock时读取已提交快照。
- 未初始化schema及尚未迁移的旧JSON账本会回退到 `BEGIN IMMEDIATE`，由写事务完成表创建和一次性导入；迁移/完整性边界保留。
- 增加两项回归：在一个写事务持有 `BEGIN IMMEDIATE` 且已有写入时，快照读取与事件页读取均立即返回上次已提交数据。
- 账本、聊天恢复、资源限制、并行工作流相关组合96/96通过。压力报告脚本见 [`scripts/stress_run_ledger_http.py`](../scripts/stress_run_ledger_http.py)。

## 混合HTTP压测

Windows 10本机，Python 3.11.9，临时目录中的SQLite及合成事件；真实FastAPI回执处理器通过Uvicorn绑定127.0.0.1。每轮16个HTTP读取worker各循环100次，共1600次读取，同时一个线程持续调用真实账本 `mark()` 并尝试每20ms写入一次（目标50次/秒）。旧策略强制所有账本访问使用 `BEGIN IMMEDIATE`；新策略仅已初始化数据走普通读事务，写入、迁移保持原行为。两种策略在同一个服务器进程内交错执行，预先做小轮预热。测试没有重试HTTP失败；非200、无效账本回执、SQLite异常或写线程未能退出均计失败。实际读请求为各4800，读/写失败均为0。

| 策略 | 每轮读取RPS | 每轮读P95 (ms) | 每轮读最大值 (ms) | 每轮完成写数 / 写RPS | 写P95 (ms) |
| --- | --- | --- | --- | --- | --- |
| 旧策略 `BEGIN IMMEDIATE` | 48.3 / 35.4 / 47.7 | 631 / 910 / 618 | 4,060 / 4,515 / 1,160 | 158 / 243 / 138；4.8 / 5.4 / 4.1 | 339 / 369 / 397 |
| 普通读事务 | 57.1 / 51.0 / 38.2 | 471 / 517 / 746 | 922 / 1,012 / 2,084 | 94 / 160 / 150；3.4 / 5.1 / 3.6 | 433 / 366 / 506 |

三轮中位数：旧策略读吞吐47.7 RPS、读P95 631ms；普通读事务51.0 RPS、读P95 517ms。普通读事务的读取改善方向存在，但第三轮P95和最大值更差；写入吞吐中位数也从4.8降至3.6次/秒，写P95未改善。样本只有三轮，期间本机负载和磁盘投影成本可显著影响结果，所以不把中位数变化宣称为确定的性能提升。写线程所说的“50次/秒”是尝试节奏，不是实际稳定写入能力。

此前0.45.7纯读HTTP突发为16并发、每轮1600请求、三轮共4800，0失败，约93–100 RPS，但最大延迟3.2–4.0秒。该结果不能与本次混合负载直接比较；它已触发对读写锁争用的检查。

## 稳定性边界

- 自动继续偏好：64个会话交错读写64,000次，无串会话或值不一致；前端专项53/53通过。
- 后端隔离可靠性组合：300通过、4个条件跳过；账本、图片队列、RPC子进程压力、资源准入和Gateway恢复热点三轮129/129通过。这些是在本补丁之前完成的覆盖；本补丁额外相关回归96/96通过。
- 本次混合回环HTTP读写各0失败，但读P95中位数约0.52秒，读最大延迟2.1秒，实际写入约3–5次/秒；没有约定SLO，不能据此判定达标。
- 没有运行长时间内存/资源曲线，没有测真实模型成功率、图片质量与费用、平台数据完整率，也没有在138正式或隔离实例压测。生产和运营稳定性仍未知。
