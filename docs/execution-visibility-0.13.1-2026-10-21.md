# 0.13.1 执行可见性修复（2026-10-21）

## 问题与已核实原因

- 命令标题原先只取首个空白分隔词，导致 `cd ... && cat ...`、`cd ...; python ...` 均显示为cd。这是确定的展示缺陷。
- 思考接收链路已有HTTP reasoning字段、Responses摘要、Anthropic thinking、网关raw事件及开头think标签适配，但页面只在正文非空时显示思考区；`thinkingStatus`未完整进入前端持久化。不能由截图直接断定特定provider没有返回摘要，或承诺一定能获得内部推理链。
- 计划原先依赖提示、其他运行器的原生工具或exec脚本回执，本地插件没有通用计划工具；`easel_goal_update`已有目标服务，但其成功步骤未纳入统一执行清单。
- 普通对话没有明确的主动分工策略。持续目标的原有预算门禁则明确禁止派生Agent，不能把此限制误报成观测故障。本轮保留它，避免未经预算确认扩大后台执行。
- 后端实际发出“运行已 N 秒没有新事件，仍在等待 provider”，前端过滤器只匹配另一种旧文案，故失败后的较早进度仍显示等待。

## 实现与入口

聊天回复内查看“思考摘要”“工作进度”“本轮行为”。命令行现在按语法概括实际操作：读取文件、搜索内容、列出文件、运行Python/JavaScript脚本或内联代码、构建、测试等；识别引号内分隔符与常见shell包装。标题不执行命令、不推测私密动机、不把动作当成功结果；未知命令保守展示可执行文件名，展开仍可复制完整命令、输出与退出码。

可见摘要继续只取服务实际提供的文字，状态通过SSE、恢复快照、本地存储与文本备份保留。未收到、历史未知和备份未核验分别说明；失败或停止时已有摘要标为中断，正常阅读的展开选择保留。提高思考档位不保证渠道或网关暴露摘要。

插件新增无模型调用的 `easel_plan_update`，使用 `plan:[{step,status}]`；验证1至32项、每项最多500字符、最多一项进行中。普通复杂任务优先3至8步，只有成功工具回执才能更新清单，失败/普通文字不能伪造完成。工具不可用时保留脚本回退。已有持续目标优先 `easel_goal_update`，普通对话不自动创建持续目标。进度工具不计为目标的实际工作，但仍消耗工具预算，不能靠反复更新进度伪造推进。

运行时说明要求在允许协作且含可独立并行任务时主动委派，主Agent同时推进其余工作；短任务、串行任务不硬凑协作。保留显式禁用、启动模型、并发、深度、时限与原任务授权。持续目标从真实session/turn状态识别，优先目标工具且明确不开放子Agent。页面默认紧凑显示计划回执及委派观测状态，可展开查看本轮启动配置、限制或历史未知；配置允许不等于工具存在，委派请求不等于真实子Agent身份，更不等于任务完成。全部观测继续按会话与轮次隔离。

新增runtime与thinkingStatus均为兼容可选字段，无数据库表迁移。回滚恢复此前源码/构建/插件目录及工作区规则并按既有方式重启；不删除原会话或执行回执，不根据历史缺字段补造状态。
