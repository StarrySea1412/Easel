# 0.45.7 隔离压力与稳定性评估

## 结论

**隔离代码路径的并发、故障保护与任务账本表现良好；整体运营/生产稳定性尚未得到证明，不能据此称为生产稳定。** 本轮没有对138生产、第三方平台或真实模型施加负载，也没有进行持续HTTP吞吐测试。

## 本轮测试

- 自动继续偏好：64个会话并发交错执行500轮读写，每轮一次写入和一次读取，共64,000次本地存储操作；最终值、会话隔离和键数量全部一致。用例运行约0.22秒。
- 前端回归：设置导航、旧偏好、运行/只读禁用、存储写失败、手动继续等测试53/53通过，约21秒。
- 后端隔离可靠性组合：300通过、4跳过，约189秒。包括真实子进程协议、取消、恢复、Gateway并发恢复、内存压力前置拒绝、图片队列幂等/渠道并发/故障接回、账本多进程接受与任务结算。
- 竞争热点复跑：账本、图片队列、RPC子进程请求压力、资源准入和Gateway恢复连续3轮，每轮43通过；总计129/129，通过时间22.42、23.16和29.67秒，没有观察到间歇性失败。
- `npm.cmd run build`、`npm.cmd run lint`和`git diff --check`此前对同一源码版本通过；lint有仓库既有warning，构建有大chunk提示。

## 范围和限制

- 后端测试用的 `websocket-client` 仅安装到系统临时目录，没有更改仓库依赖。未安装该模块时，两项依赖原生Web入口的测试无法收集；使用隔离临时依赖后，上述300项组合全绿。最初一次组合有2项导入失败，根因为测试解释器缺模块，不是测试断言发现产品缺陷。
- 四项跳过是 pytest 标记的条件用例；本轮没有安排完整环境/完整后端全量测试。最初因测试解释器缺依赖而导入失败的原生入口测试，在临时依赖可用后包含于最终组合并通过。
- 64会话压测是本地存储微基准，不表示64个在线用户或浏览器/服务端吞吐能力。
- 没有HTTP RPS/延迟分位、长时间内存曲线、真实模型成功率、真实图片收费/质量、运营数据完整性或生产负载证据。

## 稳定性判断

- 自动继续偏好设置及会话隔离：本轮验证通过，风险低。
- 被测任务账本、图片队列、资源拒绝与执行进程边界：所选隔离回归通过，风险中低；只覆盖选定故障矩阵。
- 真实供应商、平台数据、端到端内容生产及138生产：未知，本轮未测试。
- 因此当前可描述为“受控测试下核心并发与故障处理路径通过，运营级稳定性待验证”，不能给出总体成功率或SLA。

## 真实稳定性门槛

继续沿用[运营可靠性路线](operations-reliability-roadmap-2026-11-02.md)：冻结20个代表性运营任务和故障矩阵，完成受影响后端与全量回归后，在有用户授权的隔离/正式范围进行48小时有效负载观察，再累计至少7天、100个代表性任务。分别报告渠道与任务类型的完成率、失败原因、延迟、资源用量、恢复次数及费用；重复收费/发布、跨账号数据、已确认产物丢失和错误报成功必须为0。未达到这些证据前，不按生产级稳定对外承诺。
