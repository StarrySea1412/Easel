# Agent 工作室重设计调研：角色质量、可信工作过程与自定义

日期：2026-10-01，Asia/Shanghai。本文保留研究依据并跟踪实施；研究建议、样板与已验收功能分别记录。所有后续反馈（图片、分析、热点、README、运行记录）统一收录于 [工作台体验整改总清单](workspace-experience-action-plan-2026-10-01.md)。

## 结论与下一轮交付

用户指出的两项问题成立：角色造型明显有几何拼装感，角色动作与可见工作成果缺少连续联系。需要同时重做角色资产、动作组织和工作反馈。仅增加动物种类、颜色、摆动幅度，或继续扩大办公室画面，不能改善核心体验。

建议保留小动物工作室方向，采用精致、克制的风格化 3D：轮廓清晰、表情可读、衣服有结构、爪子能握持工具，动作具有注意力和重量。Three.js 可以继续使用；主要投入应放在角色与动作资产，以及真实事件到画面的连接。

下一轮先交付一个可实际操作的样板：**一名精细角色、一个工位、一个原位角色编辑器、一段完整工作过程，以及一次可追溯的真实任务。** 美术样板与任务事件接入并行开展。样板达到视觉标准后再扩展其他角色与多人办公室，避免把同样的问题复制六遍。

## 为什么现在看着粗糙

| 问题 | 现有证据 | 设计影响 |
| --- | --- | --- |
| 形体有拼装感 | `officeGeometry.ts:99` 的球体纵向只有 7 段；`:352` 起用椭球躯干、球形头和分离四肢组装角色 | 加细分只能去除棱角，无法解决肩颈、脸颊、口鼻、服装结构与关节连贯性 |
| 物种差异浅 | `officeGeometry.ts:363` 起猫、兔、狐、熊共享近似主体，主要替换耳朵、嘴与尾巴 | 换物种仍像同一个玩具换零件，缺少值得定制的角色身份 |
| 爪子无法表现握持 | `officeGeometry.ts:434` 起爪部为压扁球体；笔在 `:467` 附着到手腕 | 接触位置可能正确，但看不出握笔、扶纸、按键、托住物体 |
| 近景仍难看清工作 | `OfficeSceneRuntime.ts:235` 的默认相机及 `:407` 的近景偏移都位于角色背侧；面部朝局部 -Z | 浏览器可见大量后脑勺。近景放大同一方向，未充分展示眼神、手部和工作对象 |
| 二维编辑预览与实际模型不同 | `EmployeeAppearanceSettings.tsx:9` 为独立 SVG 肖像；3D 模型由另一套几何生成 | 编辑器中的尖脸狐狸与办公室形体不一致，用户无法判断最终效果 |

现有手臂并非完全没有接触求解。`officeAvatarMotion.ts:16` 已实现两段手臂 IK；已有测试检查骨长、笔尖接触和视线方向。问题在于：**数学上的腕点接触，没有形成可感知的握持、身体承重和连续行为。** 本轮应保留这些正确性经验，提升资产与动作质量。

## 为什么不像真的工作

| 断点 | 现有证据 | 应改变的表现 |
| --- | --- | --- |
| 动作重复且缺乏段落 | `officeAvatarMotion.ts:53` 按六秒循环 | 组织为准备、操作、检查、收尾；停顿要有原因，不让所有角色同时机械摆动 |
| 道具突然出现 | `officeAvatarMotion.ts:56` 直接切换纸、板、笔的可见性，随后直接改位置与倾角 | 增加伸手、取物、握持、放下，以及可中断的动作过渡 |
| 身体不支持手部动作 | 躯干只有很小前倾和正弦变化，腿直接挂根节点；腕部抵消旋转、笔旋转每帧归零 | 肩、脊柱、骨盆、腿随动作承重；不同工具具有不同腕部方向和握持姿态 |
| 操作对象不发生变化 | `officeGeometry.ts:454` 起纸与画板采用固定图案；`officeScreenTexture.ts:45` 主要显示任务元数据 | 屏幕应展示有证据的资料、文稿、预览或检查结果；动物动作与工作对象相互对应 |
| 短工具调用被漏过 | `officeActions.ts:30` 只采用未收到回执的调用；`useAgentOffice.ts:40` 在请求完成后间隔两秒轮询 | 短操作显示「刚完成读取」等一次性反馈，不能靠延长假工作来填补视觉空白 |
| 子 Agent 缺少本人的操作 | `agent_office.py:296` 当前公开工具事件归主 Agent | 接入经身份核验的子任务公开事件，角色才有可靠的动作依据 |
| 未上报具体步骤就静止 | `OfficeSceneRuntime.ts:114` 排除 unreported 的连续动画 | 可保留自然坐姿、呼吸和看屏幕，但状态仍明确「执行中，步骤未上报」 |

可信感来自三件事同时成立：手确实在操作对应物体；屏幕的变化对应已经发生的工作；成果和交接对应明确的任务与人员。只把状态文字换成“正在认真工作”不会产生这种可信感。

## 美术与技术路线的取舍

| 路线 | 适用性 | 本项目建议 |
| --- | --- | --- |
| 继续程序化拼装基础几何 | 迭代快，适合占位与远景简化 | 保留为降级或开发占位，不承担主角近景质量 |
| 精制、蒙皮的 GLB 角色 + Three.js | 可设计轮廓、表情、服装和动作；延续现有渲染架构 | 推荐，替换角色与动作层，保留可靠的观测、资源释放与错误降级 |
| 预渲染二维/2.5D 角色 | 可用较低运行成本获得稳定画质，但视角和换装组合受限 | 作为低性能模式的候选，不能无代价替代自由旋转与实际换装 |
| 更换大型游戏引擎 | 增加应用体积和接入成本，仍需模型与动作资产 | 当前缺口没有证明换引擎的必要性 |

美术样板的具体要求：

1. 先完成一只猫或狐狸，正面、侧面、背面、坐姿均有可辨识轮廓；肩颈、腹部、衣摆自然衔接。不同物种后续拥有各自脸型与体态，不能只替换耳朵。
2. 眼睑和视线可控；爪子至少有平放、握笔、托纸三种形态。尾巴、耳朵属于次要动作，不能喧宾夺主。
3. 毛发采用适合实时渲染的简化材质与轮廓处理；衣料、塑料、金属、屏幕表现应可区分，避免所有物体都像同一种发亮橡皮。
4. 角色、椅子、桌高、键鼠位置一起设计。定义键盘、鼠标、纸张边缘、笔握点和视线目标等接触锚点。
5. 提供可编辑源文件、GLB、贴图、骨架与动作清单。现成素材需核查许可和商用条件，并验证骨架、表情、换装、坐姿兼容性；本次未选定或购买具体资产。
6. 图片概念稿只能用于确定风格；图片转出的粗模型也需拓扑、蒙皮和动作检查，不能直接当作可交付的角色资产。

技术上使用基础骨骼动画片段，辅以头部注视和手部 IK。Three.js 的 `AnimationAction` 已有 cross-fade 与权重混合能力；但有混合 API 不代表动作自然，仍需设计好进入、循环、退出姿势和持物切换时机。不同体型的动作重定向还需逐项校正。

## 一段可验收的工作应该是什么样

下面的时间只是约 20–30 秒美术演示样板的节奏参考，不是未来后台任务的固定时长。真实模式按事件推进阶段，不能强行对齐演示时间。

| 段落 | 人物行为 | 工作对象 | 视觉重点 |
| --- | --- | --- | --- |
| 接到材料 | 转向屏幕，视线先落下，身体轻微前倾 | 打开明确的任务或材料 | 让注意力转移可见 |
| 阅读 | 眼神扫读，右手短暂操作鼠标，停下来辨认重点 | 来源条目或已收到的内容 | 手、眼、屏幕各自有对应目标 |
| 编辑 | 双爪触键，输入一小段，停顿后继续 | 已收到的文稿片段或文件修订 | 不是无休止敲键盘；没有内容流时不伪造逐字输出 |
| 检查 | 收手、回读，必要时再调整 | 文稿预览、图像或检查结果 | 形成操作与反馈的因果关系 |
| 提交 | 完成保存动作，回到自然坐姿 | 带作者、任务、版本的成果卡 | “结束运行”和“成果验收通过”分别表达 |

第二段样板再验证取笔、握笔、落笔、抬笔检查和放笔。若后台是异步生图，角色应查看生成规格与等待返回的预览，不应一直假装手绘。绘图动作适用于确有绘图或版式编辑事件的场景。

镜头应通过工位布局让脸部三分之二侧面、双手和工作对象同时可读。提供全景、工作近景、手部检查三种明确机位。显示器不要挡住脸；详细正文在同步的清晰预览区读取，避免强迫用户辨认三维屏幕上的微小文字。

## 真实任务与动画如何连接

采用三层状态：后台运行状态、任务工作阶段、视觉动作。它们有明确映射，但不能混成一个枚举。

| 取得的证据 | 可以表现 | 没有证据时 |
| --- | --- | --- |
| 本人读取/检索事件、返回来源 | 看屏幕、滚动资料；收到结果后突出来源卡 | 只显示读取状态，不编造引用与材料正文 |
| 本人文稿片段、文件修订事件 | 键盘操作、回读；显示真实版本变化 | 仅运行状态就保留自然等待，不生成假文稿 |
| 本人生图任务、产物返回 | 检查参数、等待生成、查看实际缩略图 | 不编造进度百分比，不把固定色块当成作品 |
| 含接收者的任务分派回执 | 任务卡从分派者进入接收者工作区 | accepted 只能表示已接受，不能立即演出对方完成工作 |
| 检查结果与问题清单 | 定位问题、修改标记、待复核提示 | 工具返回不等于检查通过 |
| 绑定人员/任务/版本的产物登记 | 提交成果、打开预览、显示审阅结果 | 工作区新增文件不能自动归功于某个人 |

建议事件最小字段为 `agentId / runId / taskId / operationId / eventType / actionCategory / occurredAt / targetRef / artifactRef / evidenceSource`。公开引用和摘要按需返回，不把原始命令、凭据或所有工具输出直接推给画面。

短事件采用简短的「已发生」反馈；断线后冻结工作进展并标记旧快照。恢复时先对齐最新状态，不把积压事件慢慢演成当前工作。停止或错误优先中断，允许很短的收手动作，但状态文字立即更新。

## 角色自定义重做

现在的角色卡固定七张，保存在浏览器，只改外观；它不定义提示词、技能、工作目标或输出标准。`employeeAppearance.ts:4`、`:8`、`:57` 和 `EmployeeAppearanceSettings.tsx:69` 可直接核对。品牌/创作者画像是项目背景，与员工职责应分别管理。

建议改成员工库，支持新增、复制、归档和版本；每次编辑一名员工，办公室内打开编辑空间，并保留当前任务、选中员工和镜头。左侧为实际使用的 3D 角色，右侧分组编辑：

| 分组 | 用户可以定义什么 | 必须看到的反馈 |
| --- | --- | --- |
| 形象 | 物种、体态预设、毛色/花纹、服装、合适的配饰 | 同一模型的正面、侧面、坐姿、工作动作即时预览 |
| 职责 | 负责什么、适用任务、交付格式、质量标准 | 一段清晰的员工职责摘要 |
| 能力与资料 | 可用技能、工具、模型偏好、项目资料范围 | 已连接、不可用及原因；配置实际影响后续执行 |
| 试运行 | 给一个小任务，查看执行过程、产出与问题 | 哪个模板版本、实际使用的模型、取得了什么结果 |

形象采用成套预设加有限调节，避免初版变成几十个难用的滑块。每种装备都要验证坐姿和动作，不能允许帽子穿耳朵、眼镜悬空、袖子穿手。自然动作风格可以调节，但不会被暗示为能力等级。

保存分为形象变更和工作配置变更。外观可立即预览；工作配置保存为新版本，当前任务保留启动时的版本。取消、撤销、重置针对当前员工，不再要求一次保存所有卡片。

底层需要稳定员工模板、外观配置、团队模板、一次任务指派及产物记录之间的关联。运行实例引用员工版本，而不是让用户每次给临时 Agent ID 手动认领皮肤。

## 工作室布局与实际用途

桌面端将当前任务、选中员工和下一步操作保持在容易到达的位置，提供办公室视图与任务视图；窄屏优先显示任务和员工，3D 可展开。团队规模按任务决定，简单任务可以只由一人完成。

工作室主流程为：任务简报 → 选用员工/团队 → 分工与执行 → 查看成果 → 修改要求或验收。第一次没有真实任务时显示开始任务入口，演示作为明确可选项；不要每次进入都回到模拟六人协作。

全工作区近期文件继续作为找文件功能，不能充当成员交付清单。交付清单需明确绑定任务、作者、版本和审阅状态。当前 `OfficeOutputMonitor` 不接收任务/会话身份，`office_outputs.py:119` 也明确无法推断人员归属。

## 实施顺序与验收门槛

| 阶段 | 交付 | 进入下一阶段的条件 |
| --- | --- | --- |
| 角色与工位样板 | 一个精细 GLB 角色、一个工位、工作与手部近景、同模型外观编辑 | 正侧背坐姿通过人工观感检查；脸、手、物体可同时辨认；换装无明显穿插 |
| 连续工作样板 | 阅读、键盘/鼠标、检查、收尾；再补取放笔 | 隐藏状态文字仍能分辨主要动作；道具不瞬移；切换、等待、停止、错误有合理过渡 |
| 同一角色真实试运行 | 员工配置真正生效；本人事件驱动动作；交付可追溯 | 验证一次真实执行、实际模型和产物归属；界面演示与后台执行分别记录 |
| 双人协作 | 研究员把明确材料交给文案员；下游引用上游版本 | 分派、接收、完成、返工均有证据；两个人不会因共用状态同时做相同动作 |
| 扩展工作室 | 更多物种、团队模板和合适的低性能模式 | 达到目标设备性能预算，并逐项验证菜单、跳转与角色编辑的状态保留 |

必须分别记录四种结果：几何/状态自动测试、真实浏览器观感与操作、真实后端执行、性能实测。自动测试通过不能替代“看起来像在工作”的人工验收。

候选性能目标可以先设为普通目标设备上单工位接近 60 fps、六人场景至少 30 fps，再根据实际设备确认；这只是待讨论和待测目标。需采集帧时间分布、首次可交互耗时、纹理内存和 draw calls，再制定面数、骨骼数、贴图与阴影预算。本次没有测量这些指标，不作达标承诺。

优先保留现有的真实/模拟区分、精确身份核验、过期快照处理、资源回收和 WebGL 失败降级。资产替换必须继续满足这些可靠性要求。

## 外部研究来源与采用边界

# 2026-10-01 追加研究方向

最新持笔过程：笔必须有稳定去处、接触时点和释放时点，不能随状态直接消失。主办公室已增加竖直笔座，以及伸手、提起、转向工作面、抬笔、归座、收手的短动作；笔始终为同一对象。笔座位置避开画板，握点高度由实际蒙皮净空检查确定，修复了归笔时手掌轻微穿桌。设计师取笔、暂停恢复与归笔已做真实浏览器连续抽查；六岗位/四物种几何检查及完整前端359项通过。这证明本轮笔的取放改动，不证明精细手指、纸张等全部道具自然操作或最终角色美术质量完成。下段“道具完整取放未实现”为此前短过渡阶段状态。

工作行为追加：在已有连续角色表面之上，进一步区分六岗位思考时的双手与注视；动作状态变更以短过渡连接手部目标和躯干，仍由固定长度 IK 控制。观测语义也必须准确：查看协作列表不能画成派发任务；已结束轮次不能因残留进程或旧子成员回执继续忙碌；更新中断的屏幕必须称为上次记录。现已落实这些修复，并提供画布上方的演示时间与阶段定位，便于在同一镜头比较不同工作时刻。道具完整取放、手指握持和行走仍未实现，短姿态过渡不等于这些完整动作。

最新 U13：用户已确认“接线”指身体/关节拼接痕迹。口鼻现为头部连续曲面，腮红与纹理为表面色；大腿至脚掌为同一闭合曲面；衣身与双臂最终使用单一闭合蒙皮表面，7 根骨骼驱动，消除独立肩臂网格接头。形体初始化按四物种缓存，编辑外观不重复求解；原猫尾串珠也已换成连续曲线表面。保留任务标签语义，不把本次改动理解为去掉所有任务关联线。

正面、斜侧与工作近景已做真实浏览器抽查，四物种整身连通/闭合/蒙皮和资源释放已自动验证。自然动作、逐帧全姿态自交与性能仍有后续工作；连续表面修复不等于整个角色资产制作已经结束。

## 腾讯 Marvis 已核实参考与采用方向

已通过真实浏览器读取 [腾讯 Marvis 官网](https://marvis.qq.com/) 与 [官网转载 APPSO 实测，2026-05-19](https://marvis.qq.com/news/personal-assistant-agent)。页面实图中可见：浅色开放场景、清晰投影、黑色小马轮廓和彩色颈饰；工位外还有跑步机、茶水与卫生间空间；截图里的角色分别在工位就坐和跑步机活动。文字描述六类职责、待命时打盹/散步/运动/喝咖啡、接单后拆解分派。这是公开页面与配图观察，没有安装、登录或实际执行腾讯客户端任务，也没有从静态配图推断具体骨骼/动画技术。

对 Easel 的直接结论：增加网格面数和桌面摆件不足以产生“真的在工作”的感觉。优先让身体轮廓、重心、注视、手的分工和工作/待命节奏可读；浅色场景应托住角色与工作对象，减少无意义拥挤。学习表现原则，不复制腾讯角色与品牌素材。

本轮主场景动作实施标准：研究员侧身查阅资料，文案前倾键入并停顿回读，设计师偏向画板并单手描绘，检查员转向副屏，审阅者后靠审读并指示，协调者面向团队/任务板。相同岗位也按稳定身份改变惯用侧、幅度与节奏；不能只对同一动作做时间错峰。工作动作仍依据观测动作种类表现，模拟与真实事件分开标识；待命不伪造工具执行。

近景复查追加：原腿脚的双侧位置完全对称，脚底悬空。主场景已按岗位改变双腿前后摆放与朝向，并加入匹配脚底高度的脚踏；让躯干差异延伸到完整坐姿，避免上半身变化而下半身仍复制粘贴。

用户明确指定参考腾讯的 Marvis，并指出“每个人工作姿势一样”和“超过 8 个 Agent 怎么办”。本轮先核对产品与公开演示，再决定角色美术方向；暂停沿用现有样板批量生成物种。岗位差异必须覆盖身体重心、注视、左右手分工与节奏，而不仅是工位摆件。

大团队实施前审计：原前端工位最少 8 个并可扩展，旧后端最多返回 32 人，旧前端解码超过 64 人拒绝快照。当前已移除上述人数截断，完整名单支持跨区搜索定位，场景每区最多 8 人；保留日志读取预算和覆盖限制。桌面 12/20/50 人及手机第 50 人已用模拟演示做浏览器检查；受控数据测试包含 100 人，不代表真实 100 Agent 并发或浏览器性能达标。
