# ZCode、Codex、Grok Bot 与 DeepSeek Harness：Easel 接入取舍

日期：2026-10-22；后续实施增量见文末。状态：**调研与方案修订完成，正分批实施与验收，完整目标未完成**。

关联：[推理与画像记忆接入方案](inference-memory-integration-plan-2026-10-21.md)、[用户需求清单](user-requirements-2026-10-08.md)。用户补充“不一定有开源，你得找一下了”，因此同时考察公开产品行为、官方接口和开源实现，不以有无仓库决定是否值得借鉴。

## 1. 结论与比较边界

建议把原方案扩展为“任务执行可靠 → 跨页事实一致 → 目标按证据验收 → 经验按范围积累 → 工具协作可交接”。缓存度量与消息边界仍保留；缓存比例不应排在运行恢复与数据一致性之前。

四个对象处在不同层次，不能给一个缺乏实测的总分：ZCode 是开发工作台；Codex 有客户端和可嵌入的执行协议；Grok Bot 是长期工作的助手产品；DeepSeek Harness 是可组合的 Agent 运行框架。Easel 的比较标准应是能否完成账号、内容分析、生图、发布草稿、结果回填的业务链，而不只是编码分数。

本轮实际读取官方网页和固定版本的公开仓库文档；Easel 对照 `codex/upstream-merge-0.8.0` 的 `8d636eb4`，产品源码仍为 `5b6e8177` / 0.11.2。没有登录竞品执行同题测试，也没有性能、成本或质量对跑。旧文档里的“缺少”不直接作为当前结论。

## 5. 接入系统的具体设计

### 5.1 先让同一任务在各页读到同一事实

复用现有ID，逐个领域确立唯一写入入口，统一关联 `taskId/goalId`（无目标可为空）、`sessionId/turnId`、`engine/providerRunId`、`profileId/accountId`、`revision/eventSeq`。原有事件只有作用域内的序号时，不能跨日志直接比较大小。

前端事件负责提示哪些查询失效；客户端缓存按账号、画像、会话和任务分键，保留旧数据并显示 loading icon。事件断流/多标签页/刷新后按持久快照与游标补读，禁止把本地缓存当在线事实。删除使用持久删除标记与版本屏障，通知和晚到结果均不能复活已删除会话。

在已有存储上按领域渐进增加可靠事件发布。若某领域迁到 SQLite，则事实更新和待发布事件同事务提交；不要声称“JSON写入后发一个浏览器事件”具有事务一致性。账本及旧JSON保留兼容读取，迁移有备份、schemaVersion和回滚路径。先做任务/分析/通知的关键链，不一次重写全部历史会话。

恢复流程先判断：服务是否存活、执行是否仍由有效 owner 持有、供应商是否已接受请求、已有回执是否能关联。浏览器重连只恢复观察；服务重启先对账，不直接重发模型请求或发布。只在证明未接受或供应商具幂等契约时重试；无法确认的执行保留为待核验，并允许用户显式决定后续动作。

### 5.2 统一执行控制，但按能力显示

建议给现有路径增加可选能力声明：`steer`、`interrupt`、`resumeObservation`、`resumeExecution`、`nativeGoal`、`dynamicTools`。每项带已检测版本/适用范围，未知不伪装成已支持。能力声明描述执行控制，不能用“尚未检测”封禁普通模型选择或正常发送。

Codex 优先复用现有 App Server 路径；本机确认支持后，目标可由原生接口管理，Easel映射状态与业务验收。若选择 Easel 外层续跑，就不同时打开原生自动目标。OpenClaw 保持既有目标控制；未支持的 steer 不能伪装成功，更不能偷偷改用默认模型。

停止操作要同时覆盖目标调度、活动轮次和所属子任务；已结束与资源已释放分别记录。目标完成须依据该目标/材料版本的证据，不按“模型说完成”或收到一段报告判完成。发布草稿完成、等待确认与平台发布成功分别验收。

### 5.3 记忆分四层，明确哪些可自动写

| 层次 | 保存内容 | 隔离与写入规则 |
| --- | --- | --- |
| 当前任务/会话 | 目标、待办、原材料、阶段结果、恢复检查点 | 按任务/会话保存事实；压缩摘要不自动升格为长期经验 |
| 项目知识 | 稳定流程、术语、团队纠正、项目约束 | 默认按项目隔离；用户明确“记住”按授权直接保存，自动抽取先做候选；强制规则另走项目规则配置 |
| 画像与账号经验 | 人设风格、禁忌、平台/账号效果结论 | 按画像及必要账号范围读取；有来源、版本和失效记录；跨账号复用须明确适用范围 |
| 工具/运行诊断 | 某协议兼容条件、故障分类、验证版本与日期 | 独立存放、脱敏并限时复查；不混入创作风格，也不自动更改网关/凭据 |

参考 ZCode 的小条目/索引与 Codex 的读写分控，落在原方案经验服务，而不是自动导入用户本机两种产品的记忆目录。自动提取按来源版本和任务状态去重，任务未收尾不反复总结；单独记录提取用量，额度不足延后。建议配置“读取经验”“生成待确认经验”两个独立选项，具体默认值在实施时沿用用户已有偏好。

候选被材料中的“记住此规则”触发，不构成用户授权。外部材料、历史输出和诊断只能作为数据，不提升权限；与当前明确要求冲突时记录冲突并按当前要求处理。缺来源或不可比数据，不写“有效爆款策略”。确认、撤销、修订仍按原方案服务端校验和版本控制执行。

### 5.4 把 Grok Bot 的角色协作转成实际内容流程

建议以已有账号分析、生图工坊、发布中心为工具角色，而不新建一组装饰性机器人：

1. 账号/作品分析产出带材料版本的结论与候选方向，回填原分析面板。
2. 策划接受选定方向，产出可编辑稿件；交接保留任务、来源和原对话链接。
3. 生图接收指定稿件/提示词版本，产物进入内容库，可回对话作附件，不自动发送。
4. 发布中心接收稿件与素材，沿用账号预检和最终确认；回执绑定本次发布任务。
5. 后续获得同口径效果数据才生成经验候选；发布成功本身不证明策略有效。

建议最小交接记录为 `handoffId/taskId/sourceSessionId/sourceRole/targetRole/artifactId+version/scope/acceptance/status`，附现有模型路由与预算约束。接收方确认后才转移执行归属；重复接收幂等、取消可传递、失败保留已生成产物。可串行完成就不为展示协作而强行多模型并发。

Grok Bot 文档明确同账号 Bots 共享电脑/文件/浏览器登录态，但对话和学习上下文按 Bot 分开 [G1]。Easel不据此推断“多个平台账号可以共用权限”：工具读取和执行仍需校验任务所属画像、账号和凭据范围。

下列为2026-10-22制定的实施计划，按文末增量记录当前实现与验收；未逐项证明的门槛继续保留。保留原批次编号，避免历史清单对不上。

已有后端全量175失败、54错误仍是未完成归因项（上一轮回执，非本轮重跑）。任何批次上线前须处理受影响的新增回归和迁移风险，不能以本文方案、HTTP可达或构建通过代替业务验收。
