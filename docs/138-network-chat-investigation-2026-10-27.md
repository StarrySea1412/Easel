# 138 网络提示与聊天失败排查

日期：2026-10-27（北京时间）。范围：只读查看正式服务、失败回执和代码，并进行少量无凭据网络探测及纯函数复现。未重启、部署、修改服务器配置或发送新的模型生成请求。

## 聊天截图的直接原因

用户截图显示 `chat_recovery_unavailable`。正式运行版本为 **0.14.2**，revision 为 `15c763550657bee6cee43d1caae0baa7644b147c`，镜像为 `sha256:48486786899f052b74e5053d8fe1ddf4c7714a4587014aaa2cd07ceb1a77ecfe`。app/browser 健康；app 重启计数为 0。

正式失败回执中最近三次聊天呈现同一条失败链：

| 时间 | 请求 | 结果 |
| --- | --- | --- |
| 14:43:32 | `POST /api/chat/stream` | 32ms，HTTP 500，TypeError |
| 14:44:00 | `POST /api/chat/stream` | 40ms，HTTP 500，TypeError |
| 14:45:02 | `POST /api/chat/stream` | 33ms，HTTP 500，TypeError |

共同位置为正式镜像的 `web/app.py:4454` → `easel/browser_bridge.py:56`。聊天在组装共享浏览器使用说明时，把 `Path` 对象直接传给 Linux 的 `shlex.quote`。该函数要求字符串，因此抛出：

```text
TypeError: expected string or bytes-like object, got 'PosixPath'
```

在正式容器中提取并单独执行原有 `instructions` 纯函数，使用诊断会话名，能够复现同样异常；没有发送聊天或模型请求。Windows 分支会先转换成字符串，因此本机正常不能证明 Linux 正常。

每次 POST 失败后，`GET /api/chat/jobs/{turn_id}/stream` 均返回 404。前端无法取得本轮可恢复结果，最终显示截图中的接回失败。此次请求在发给模型之前已经失败，与选择的小红书技能或附件内容无关。截图没有轮次 ID，但最近三次正式聊天的失败链与界面现象一致。

当前本地工作区已有将路径统一转为字符串的在途修改；它尚未部署到138，不能报告正式故障已经修复。

## 最初的 errno 101 提示

正式代码中，完整文案“网络错误：…”来自模型列表发现函数 `_discover_models`，表示服务端访问上游 `/models` 失败。

现场分别从宿主机及正式 app 容器探测五个已配置服务域名，仅使用无凭据 GET 和 TCP 连接：

| 检查 | 结果 |
| --- | --- |
| 宿主机、容器 IPv4 TCP | 五个域名的抽样地址均连接成功 |
| 宿主机 IPv6 TCP | 两个带 IPv6 记录的服务域名均连接成功 |
| 正式容器 IPv6 TCP | `windhub.cc`、`image.mlgb7.com` 均立即报 errno 101 |
| 正式容器 IPv6 路由 | 仅回环记录，无可用公网出口 |
| 默认 HTTP 请求 | 收到 HTTP 401/403；本次没有复现默认请求的 errno 101 |

这证明容器 IPv6 出站缺失，能够产生用户最初提供的底层错误。但缺少那一次操作的具体目标与时间，无法认定当时请求的唯一原因。IPv4 失败后再尝试 IPv6 时，Python 也可能最终只呈现 IPv6 的错误。HTTP 401/403 仅证明收到 HTTP 响应，不能证明凭据、模型列表或生成服务可用。

## 独立的供应商故障

今天网关还记录了 `deepseek-v4.1-flash`，以及部分 `gpt-5.6-luna` 请求的 HTTP 503。DeepSeek 的供应商回执为“分组 福利分组 下模型 deepseek-v4.1-flash 无可用渠道（distributor）”。这是已收到的上游响应，属于供应商渠道不可用；不能据此解释上述在本地提示组装阶段即崩溃的聊天请求。

## 后续处理边界

聊天恢复需先将经过 Linux 回归的路径类型修复按独立补丁交付并部署到138，再验证实际聊天链路。模型获取需关联具体失败服务，按实际需求选择容器 IPv6 出站配置或可靠的地址连接回退。供应商 503 需核对该账号分组下模型的可用渠道。以上修复、正式切换与真实模型验收均未在此次只读排查中执行。
