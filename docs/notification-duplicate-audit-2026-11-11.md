# 事件通知重复调查 · 2026-11-11

用户截图询问“这里会出现消息重复的问题吗”。本轮只读核对138正式通知库和已部署0.49.7 / d30b245a对应源码；没有清空、标记已读、重放对话、调用模型或重新部署。

## 截图中的同名记录

- 正式库当前109条通知，其中100条对话通知；通知id重复0，同会话/同轮次/同结果重复0。
- 2026-11-11 13:03:45、13:04:47、13:06:12三条同名完成通知属于同一会话的三个不同turnId。11:45的同名完成通知属于该会话的第四个turnId。
- 因而截图这些条目不是同一完成事件被重复插入，而是每轮结束各留一条，界面仅显示会话标题和“已完成”，没有区分轮次。服务端读取时还会按会话当前标题投影历史完成通知，标题相同不能作为事件重复的依据。
- 这项核对只判断通知身份，不证明不同轮次的用户输入或业务内容是否相同，也不证明实际平台投稿成功。

## 确实存在的去重边界

前端`web/frontend/src/App.tsx`与后端`easel/notifications.py`当前均生成`chat:<sessionId>:<turnId>:<outcome>`。前端seen集合及服务端SQLite的seen/id唯一约束能阻止相同id重放，但结果不同会生成不同id，列表不会把它们合并为同一轮的终态。

只读历史核对发现4组同一会话、同一turnId先“已完成”后“已停止”的双记录：

| 日期 | 已完成 | 已停止 |
| --- | --- | --- |
| 2026-11-06 | 15:09:17.666 | 15:09:20.733 |
| 2026-11-05 | 15:29:57.699 | 15:30:00.217 |
| 2026-11-04 | 17:05:53.866 | 17:05:54.362 |
| 2026-10-28 | 13:41:11.052 | 13:41:11.295 |

时间均为北京时间。这些是旧版本时期的历史记录，不能说是本次0.49.7上线产生；但当前源码仍使用相同去重键，独立临时目录复现确认该边界仍在：同一轮同结果调用两次只有1条，再传同一轮stopped=True后为2条，另一个新轮次后为3条。仅验证通知存储行为，不足以判断历史两次上报各自来自哪个写入方或哪一个状态才是权威结果。
